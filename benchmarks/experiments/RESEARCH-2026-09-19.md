# Remaining optimization candidates — 2026-09-19

Follow-up status: Intel Runtime 26.35 / IGC 2.41.5 was qualified in M09 and
promoted. The mixed INT4/FP16 GDN projection prototype was implemented and
rejected at the small operator gate in [M10](m10-gdn-projection/README.md):
15/15 numerical cases passed, but graph device latency was 1.9–2.8x the native
pair. No M10 serving or long coding benchmark was started. The text below
records the research state before those experiments.

Research only: no production change, image build or inference experiment.
Required context remains 200,704 tokens (196 Ki tokens); MTP4 stays fixed,
DFlash2 is rejected, power remains 180 W, and vision/APC remain requirements.

## Recommended next screen: QK-normalization/RoPE/gate fusion

Upstream [vLLM PR 56096](https://github.com/vllm-project/vllm/pull/56096)
merged on September 16 at `ccbaed5b91e09f528180db363af7ebb9d4fafe32`
(merge state verified through the live GitHub API; the web index still shows an
older open snapshot). It extends the Qwen3Next attention fused Triton dispatch
from CUDA to CUDA or XPU. Qwen3.5/Qwen3.8 reuse that attention implementation.

The installed production `qwen3_next.py` still gates
`use_fused_qk_norm_rope_gate` on `current_platform.is_cuda()`. Its existing
FP16/BF16 and text/mRoPE checks are present. Thus the optimization is absent
from the executing package, not just missing from a repository checkout.

The PR reports B70 Qwen3.5-9B region device time of 2.42 -> 1.09 ms for
batch-eight decode and 31.93 -> 24.57 ms for 8192-token prefill. These are
operator-region measurements, NOT a 55%/23% whole-model throughput improvement
and NOT results on our 27B MTP4 workload. A related text-only TP2 proposal
[53989](https://github.com/vllm-project/vllm/pull/53989) reports only about 0.4%
end-to-end throughput improvement in a different setting, illustrating the
importance of end-to-end validation.

Proposed screen: narrow opt-in backport on the pinned image; validate actual
FP16 shapes and mRoPE/vision output, verify dispatch reaches the fused path,
then paired fixed-request 8K/64K/128K timing and the 200,704-token boundary.
Q128/M04 attention computation is a different stage from this QK/RoPE preamble,
so coexistence is plausible but not yet tested. Promote only after measured
serving benefit, correct cache/tool/vision behavior and preserved context.

## Other current upstream changes

- **New Intel userspace pair:**
  [Compute Runtime 26.35.39758.10](https://github.com/intel/compute-runtime/releases/tag/26.35.39758.10),
  released September 17, uses
  [IGC 2.41.5](https://github.com/intel/intel-graphics-compiler/releases/tag/v2.41.5),
  released September 10, with LLVM 22.1.8. Production currently has
  26.31.39395.13 / 2.40.13. A separate container-only paired comparison is
  possible after package compatibility checks. No B70 Qwen speedup is established
  by the release notes; lower priority than the concrete fusion. Keep this
  independent of the fusion screen and leave the host driver unchanged.
- **Per-row XPU RNG:**
  [kernel PR 590](https://github.com/vllm-project/vllm-xpu-kernels/pull/590),
  merged September 10, adds device per-row seed/offset input. Installed vLLM
  still falls back for per-request generators, so a kernel update alone will
  not enable this. Its published gains compare batched versus separate per-row
  calls on B60; batch-one gain is only 1.01x. Low priority for our single-agent
  workload, and sampling/rejection semantics require explicit validation.
- **Not directly applicable:** kernel PR 584's wider chunk-prefill tile targets
  particular odd multiples of 32; our physical page size is 1664 (a multiple
  of 64) and Q128 already uses KV32. PR 595's reported activation gains use
  narrow MoE shapes; our dense FFN width is 17408. Multi-GPU all-reduce patches
  do not benefit our one-card setup. None is a demonstrated speedup here.
- Release APIs currently list vLLM 0.29.0 and XPU kernels 0.1.14/0.1.14.1 as
  the most recent published release entries. Production is already on those
  versions; newer main-branch changes need individual qualification.

## Audit of the local plan

Actual results supersede older "next step" paragraphs:

- Batch/prefill screening, Q128 and shared-KV M04 were completed; successful
  attention changes are already active.
- Sampler seed handling was screened on September 12. Small-k/top-p proposals
  were also implemented and rejected on September 14, including the later
  `smallk-d-180w` study: fast versions failed boundary semantics, conservative
  versions fell back for the entire actual top-p workload. Do not present
  these as untested ready-made optimizations.
- Small-M GPTQ, INT2 draft, direct-output and retention-interval-zero experiments
  have rejection evidence. Target-head INT4 did not establish a completed-task
  advantage. DFlash2 fails the required context capacity and is closed.
- **GDN projection fusion remains an unimplemented development idea.** The
  `smallk-d-180w/AUSWERTUNG.md` report explicitly leaves phase G conditional.
  Installed `qwen_gdn_linear_attn.py` still calls `in_proj_qkvz(hidden_states)`
  and `in_proj_ba(hidden_states)` separately. Combining them might reduce
  launches/input reads, but GPTQ packing, different precisions and downstream
  layouts must be checked first; no measured gain or drop-in patch exists.
- **State-copy/graph work** remains conditional on profiling an actual expensive
  transition; absent profiler events are not evidence of removable overhead.
- Calibrated FP8 cache and lower-precision recurrent state studies were mentioned
  but are principally quality/memory work. They are not established decode
  optimizations and are lower priority while preserving stable 196K context.

smallk-d-180w,vllm029-combined,vllm029-qualification,pro-adaptation}` and the
