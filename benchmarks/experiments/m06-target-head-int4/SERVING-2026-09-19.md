# INT4 target-head serving screen — 19 September 2026

The repaired candidate serves Qwen3.8-27B with MTP4, vision, tool calling and prefix caching at the unchanged 200704-token API limit. It is faster in this small synthetic decode screen and uses less weight memory. Production remains on the original FP16-target M04 image.

## Repair

The inner language-model loader is called repeatedly as checkpoint prefixes alternate. Packing/freeing its head inside that method used incomplete loading boundaries. Packing now happens once after the outer multimodal loader consumes the entire iterator; missing head weights and later reloads are rejected.

A real GPU start then exposed the second dependency: the executing V2 `load_eagle_model` shares the target head with the MTP draft. The older Step3.5 separate-head path is not the one this profile executes. The packed tuple now lives on the shared head module, and the draft builder adopts exactly that tuple instead of quantizing an empty FP16 parameter. This retains the existing draft quantization algorithm and removes duplicate packing.

## Throughput

One B70 at 180 W, same GPTQ body/revision, FP8 KV, MTP4/full vocabulary, Q128/M04, batch budget 4096, max sequences 1. The image IDs are pinned in the [machine-readable results](serving-results-20260919.json). Order: candidate/control/control/candidate. Each point follows a full-length warmup and has a distinct early prompt prefix; all measured requests had zero prefix-cache hits and exactly 512 output tokens. Rates use native vLLM decode counters.

| 8,192 | 2 | 78.55 | 88.41 | +12.55% | 5.56 | 5.54 |
| 65,536 | 2 | 61.38 | 64.50 | +5.08% | 66.86 | 66.74 |

Medians at 8K/64K; single points at 128K. At 8K the candidate ranged from 83.25 to 93.57 tok/s; at 64K the control ranged from 59.81 to 62.95. These are screening estimates, not confidence-bounded speed claims. Mean acceptance also changes, so the throughput difference is not a pure kernel comparison. Prefill is effectively unchanged; these percentages must not be described as end-to-end coding-task speedups.

## Memory and functional checks

| Metric | FP16 target | INT4 target |
|---|---:|---:|
| Model-loading memory | 17.69 GiB | 15.94 GiB |
| Calculated KV pool capacity | 213,699 tokens | 284,450 tokens |
| Configured API context limit | 200,704 tokens | 200,704 tokens |

The larger pool is a startup calculation, not a filled 284K request. Filled contexts were tested through 131072 input tokens. The 200704-token boundary was not exercised in this screen.

Both arms passed screenshot verification and code-fix extraction, parsed tool calling with a tool-result follow-up, and a three-request prefix-state check. The latter used 17666-token prompts and verified cold misses followed by 13312 reused prefix tokens and correct distinct retrieval answers.

Candidate: 3/3 short coding tasks passed. Control: 2/3; `merge_intervals` merged adjacent integer intervals `[1,10]` and `[11,12]`, while the fixed test requires overlapping intervals or equal endpoints. This small task set, including its edge-case interpretation, is not evidence that INT4 is generally better at coding. All code was tested in CPU-only containers without network or workspace mounts.

Teacher-forced reference scoring, three short English/code/German texts, 125 scored tokens total:

| Metric | FP16 target | INT4 target |
|---|---:|---:|
| Token-weighted NLL | 1.632499 | 1.644586 |
| Perplexity on this sample | 5.116645 | 5.178863 |

INT4 increases sample perplexity by 1.22% (NLL +0.012087 nats/token). This corpus is too small to establish broad quality equivalence. Target-head quantization changes the target distribution; broader held-out scoring and representative long coding tasks are still required before considering production promotion.
