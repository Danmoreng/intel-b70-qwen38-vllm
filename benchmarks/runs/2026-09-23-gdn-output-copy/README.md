# vLLM #47842: GDN output layout on the production XPU stack

The [upstream change](https://github.com/vllm-project/vllm/pull/47842) removes
reshapes around the GDN output norm. The research report proposed profiling
the current vLLM 0.30 XPU path first and applying the patch only if an extra
standalone copy/reshape kernel was present. This screen was run on 2026-09-23
against production image
`sha256:cd6562f03c8328fe60ca69269d0e4175a284859e56525950fbfc021be19d73f3`.

## Short serving trace

One diagnostic instance used the exact production image and serving arguments,
with XPU graphs disabled so the PyTorch profiler could expose the decode
kernels. It handled one 4,111-token prompt and 32-token greedy completion in
9.06 seconds. Production was stopped during the trace, then restored and
verified healthy on the original image. The trace captured 279,379 events and
14,945 device kernels, including 528 GDN `gated_delta_rule` dispatches.

No standalone copy or memcpy kernel occurred in the next three device
dispatches after any of those 528 GDN dispatches. The following kernels were
the fused GDN output norm/projection path. The 356 separately attributable
FP16 vector copies had `[4,5,6,256]` or `[5,4,6,256]` shapes, which are
attention layouts, not the GDN output `[tokens,5120]`. Eighteen more FP16 copy
kernels had no CPU shape association in the trace and were not attributed.
Kernel names containing `_to_copy` are fused Triton kernels; their names alone
do not indicate a separate copy dispatch. See
[`trace-analysis.json`](trace-analysis.json), generated by
[`analyze_trace.py`](../../experiments/m18-gdn-output-copy/analyze_trace.py).
The raw 5.2 MB profiler trace is retained locally in the ignored
`benchmarks/experiments/m18-gdn-output-copy/runs/trace-20260923-v030/trace/`
directory.

## Isolated output-path comparison

The local [`probe.py`](../../experiments/m18-gdn-output-copy/probe.py) compared
the current reshape sequence with the PR's direct 3D `RMSNormGated` call.
It used the production 48 heads × 128 head dimension and 5,120 output width,
with a dense FP16 projection as a stand-in for the production quantized one.
Both paths produced matching output. The medians below use 16 alternated XPU
event timings per path; the probe is a diagnostic, not a serving benchmark.

| Mode | Current | Proposed | Device kernels per call |
|---|---:|---:|---:|
| Eager | 0.3046 ms | 0.2957 ms | 13 / 13 |
| `torch.compile` | 0.2220 ms | 0.2221 ms | 2 / 2 |

The compiled case matches the production path more closely and shows no
measurable advantage or removed dispatch. The raw samples and profiler kernel
names are in [`probe.json`](probe.json). The eager difference does not establish
a serving improvement because production uses compiled kernels.

## Decision

The report's required copy-kernel condition was not observed on this XPU
stack. Do not port #47842 or run a longer serving A/B for this change. This
does not claim the PR is ineffective on the hardware where it was developed.
